# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A serverless **RAG "digital twin"** — a chat avatar that answers questions about Muhammad Salman in the first person, using only ingested facts (no hallucination). The stack is 100% Infrastructure-as-Code on AWS: Bedrock (Titan embeddings v2 + Nova Lite LLM), RDS PostgreSQL with `pgvector`, Lambda, API Gateway, and a Next.js frontend on Amplify. Region is `eu-central-1`; Lambdas run `arm64`.

## Architecture (the parts that span files)

Three Lambdas plus a frontend, all provisioned by Terraform:

1. **API Lambda** — [lambdas/api/main.py](lambdas/api/main.py). FastAPI wrapped by Mangum. Serves `/chat`, `/health`, `/warmup`. Builds a LangChain history-aware RAG chain: rewrite query → embed → `pgvector` similarity search (`k=5`, collection `digital_twin_docs`) → generate. The `AIEngine` singleton is initialized once per warm container; an EventBridge ping to `/warmup` every 5 min keeps it hot. DB credentials come from Secrets Manager (cached 15 min in-memory), never hardcoded.
2. **Ingestion Lambda** — [lambdas/ingestion/lambda_function.py](lambdas/ingestion/lambda_function.py). Triggered by `s3:ObjectCreated` on the knowledge-base bucket. Downloads the file (with path-traversal-safe filename sanitization + extension allowlist), chunks (1000 chars / 200 overlap), embeds, and writes to the same `pgvector` collection.
3. **Breaker Lambda** — [lambdas/breaker/lambda_function.py](lambdas/breaker/lambda_function.py). Automatic abuse defence. Two EventBridge rules on the `digital-twin-api-abuse` alarm target it: `ALARM` → set the API stage throttle to `0/0` (everything 429s at the front door, unbilled); `OK` → restore `5/10`. Auto-reopen is safe because API Gateway's `Count` metric includes rejected 429s, so the alarm only clears once the flood actually stops. Deliberately **not** in the VPC — it must reach the API Gateway control plane even if VPC networking is the thing failing. Manual override: `aws lambda invoke --function-name digital-twin-breaker --payload '{"action":"reopen"}' ...`; a `terraform apply` also restores the declared throttle.
4. **Frontend** — Next.js App Router in [frontend/src/app/](frontend/src/app/), **locale-segmented under `[lang]`** (`en` | `de`). Each route is a thin server component that resolves the locale and passes a dictionary into a `"use client"` component: [\[lang\]/page.js](frontend/src/app/[lang]/page.js) → [portfolio-client.js](frontend/src/app/[lang]/portfolio-client.js) (light theme by default), [\[lang\]/avatar/page.js](frontend/src/app/[lang]/avatar/page.js) → [avatar-client.js](frontend/src/app/[lang]/avatar/avatar-client.js) (forces dark), which POSTs `{message, history, lang}` to `${NEXT_PUBLIC_API_URL}/chat`. [\[lang\]/layout.js](frontend/src/app/[lang]/layout.js) **is** the root layout — there is no `app/layout.js` above it — and it owns metadata, canonical + `hreflang`. Hosted on Amplify (SSR / `WEB_COMPUTE`) and served at the custom domain `msalmansaeedch.de` (apex + `www`).

**Data flow:** edit files in [data/](data/) → push → [.github/workflows/data_sync.yml](.github/workflows/data_sync.yml) runs `aws s3 sync ../data s3://<bucket> --delete` → S3 event fires the Ingestion Lambda → vectors land in RDS.

### Non-obvious things that will bite you

- **The repo layout is `lambdas/api/` and `lambdas/ingestion/`, not `backend/`.** There is no `rag_pipeline.py`, `database.py`, or `ingestion.py`, and the frontend is **JavaScript (`.js`), not TypeScript** — don't assume otherwise from framework conventions.
- **An empty knowledge-base bucket fails silently as hallucination, not an error.** The RAG only grounds answers if `data/` has been synced to the KB S3 bucket *and* the ingestion Lambda has populated `pgvector`. If the bucket is empty (e.g. after a `terraform` rebuild recreates it — the data-sync workflow only fires when `data/` files change on push), retrieval returns 0 docs, `{context}` is empty, and Nova Lite answers from its own priors instead of erroring. Symptom: generic, plausible-but-wrong first-person answers. Fix: `aws s3 sync data/ s3://<kb-bucket>/` to re-trigger ingestion.
- **Two copies of ingestion logic exist and must be kept in sync manually:** [lambdas/api/ingest.py](lambdas/api/ingest.py) is a *local* one-shot script (reads `data/`, needs `DATABASE_URL`), while [lambdas/ingestion/lambda_function.py](lambdas/ingestion/lambda_function.py) is the *deployed* S3-triggered version. They share chunking/embedding logic but are separate code.
- **The deploy branch is `main`, and its name is hardcoded in several places** that must change together if ever renamed: `on: push: branches` + the `GIT_BRANCH`/`TF_VAR_git_branch` env + the apply-gate `if:` in [.github/workflows/terraform.yml](.github/workflows/terraform.yml); `on: push: branches` + `GIT_BRANCH`/`TF_VAR_git_branch` in [.github/workflows/data_sync.yml](.github/workflows/data_sync.yml); and the `git_branch` variable **default** in [terraform/variables.tf](terraform/variables.tf) (CI overrides it via `TF_VAR_git_branch`). It drives OIDC trust ([terraform/oidc.tf](terraform/oidc.tf)), the Amplify branch, and CORS origin locking ([terraform/api.tf](terraform/api.tf)). `terraform apply` in CI only runs on push to this branch.
- **Lambda zips must be byte-deterministic** or Terraform sees perpetual drift. Both [lambdas/api/build.sh](lambdas/api/build.sh) and [lambdas/ingestion/build.sh](lambdas/ingestion/build.sh) normalize all file timestamps to `2020-01-01` and sort entries before zipping. Don't add non-deterministic steps.
- **`build.sh` caches by checking for `build/langchain`** — it skips `pip install` if the build dir already looks populated. To force a clean rebuild, delete the `build/` directory first.
- Lambda deps are installed with `--platform manylinux2014_aarch64 --python-version 3.12` (arm64 cross-build); zips deploy via the deployments S3 bucket to bypass the 50 MB API limit.
- **The retrieval query is translated to English; the answer is translated back.** These move in opposite directions and are two different prompt inputs: `query_language` decides whether the rewrite step runs, `answer_language` decides what the reply is written in. `create_history_aware_retriever()` was replaced by a hand-built `RunnableBranch` in [main.py](lambdas/api/main.py) for exactly this reason — it short-circuits to the raw input whenever `chat_history` is empty, which is the common case and precisely when a German question reached the English vectors untranslated. The branch now rewrites when there is history to resolve **or** the question is not English, and still skips the extra LLM call for a plain English first question. The rewrite is tagged `query_rewrite` so `StageTimer` bills it to `rewrite_ms`; without that tag it would silently inflate `generate_ms` and break the timing breakdown.
- **Bilingual, but the knowledge base is English-only.** The twin answers in English or German, yet `data/` and the `pgvector` chunks stay English: a German question is still embedded and retrieved against English vectors (matching German-to-English scores noticeably worse), and only the *final generation* switches language via the `answer_language` prompt variable. That variable is passed **per request** — `_engine.rag_chain` is built once per warm container and shared by every caller, so it can never hold one language. `SUPPORTED_LANGUAGES` in [lambdas/api/main.py](lambdas/api/main.py) is the source of truth; `ChatRequest.lang` defaults to `"en"` so older clients keep working and frontend/backend can ship in either order. Do **not** "fix" German answers by adding translated files to `data/`.
- **Adding a locale touches three places:** `LOCALES` in [frontend/src/app/dictionaries/locales.js](frontend/src/app/dictionaries/locales.js) + a new dictionary JSON, `SUPPORTED_LANGUAGES` and the `lang` `Literal` in [lambdas/api/main.py](lambdas/api/main.py), and the Amplify `custom_rule` redirects in [terraform/amplify.tf](terraform/amplify.tf). Canonical/hreflang and the sitemap derive from `LOCALES` via [frontend/src/app/seo.js](frontend/src/app/seo.js), so they need no edit. [en.json](frontend/src/app/dictionaries/en.json) and [de.json](frontend/src/app/dictionaries/de.json) must stay **key-parallel** — a missing key renders `undefined`, there is no per-key fallback (`getDictionary` only falls back for an unknown *locale*).
- **Every localised route needs its own `generateMetadata`.** Metadata merges *shallowly* down the segment tree, so a page with none inherits the layout's `canonical` — which is how `/de/avatar` once declared itself a duplicate of `/de` and dropped out of the index. Use `localeAlternates(locale, path)` from [seo.js](frontend/src/app/seo.js), and restate `openGraph` **in full** when overriding it: a partial object replaces the parent's outright and silently drops `images`.
- **Client components must import locale helpers from `dictionaries/locales.js`, never `dictionaries/index.js`.** `index.js` statically imports `en.json` and `de.json`; pulling even `otherLocale` from it into a `"use client"` file drags **both** full dictionaries (~18 KB) into the browser bundle, on top of the one already inlined in the page's RSC payload. `locales.js` holds `LOCALES`/`DEFAULT_LOCALE`/`isLocale`/`otherLocale` with no JSON import for exactly this reason. Check with `grep -rlF "willkommen in meinem Portfolio" .next/static/chunks/*.js` after a build — a hit means the split has been undone.
- **`dynamicParams = false` in the `[lang]` layout is load-bearing, not a perf tweak.** Without it `[lang]` matches any first segment, so `/avatar`, `/foo` and every typo would render the portfolio with `lang="avatar"` instead of 404ing — unlimited duplicate pages for search engines. Both locales are prerendered by `generateStaticParams`.
- **Pre-i18n URLs (`/`, `/avatar`) are redirected in two independent layers.** Amplify `custom_rule` 301s handle it at the edge for real visitors; [frontend/src/app/page.js](frontend/src/app/page.js) is the in-app fallback that makes `next dev` behave the same locally. Both exist because links to the bare paths are already shared publicly — keep them in sync.
- **There is now a browser test for the i18n behaviour**, the one part of it that static checks cannot see: `cd frontend && npm run build && npx next start -p 3100 &`, then `npm run test:i18n` ([frontend/tests/i18n.test.js](frontend/tests/i18n.test.js), 26 assertions), `npm run test:chat` ([chat.test.js](frontend/tests/chat.test.js), 25 assertions, `/chat` stubbed so it never hits Bedrock) and `npm run test:i18n:sweep` ([i18n-sweep.js](frontend/tests/i18n-sweep.js)). The sweep diffs every visible string and attribute between `/en` and `/de` and prints the ones that are identical — that is how the untranslated chat disclaimer and the `"Start listening"` aria-label were found, both invisible to a `grep` of the JSX. Expect proper nouns (company names, dates, AWS cert titles, job titles) in its output: those stay in the component on purpose so they cannot drift between languages. It needs `playwright` (a devDependency) plus a one-time `npx playwright install chromium`.
- **The portfolio's locale toggle is a plain `<a>`, not `<Link>` — keep it that way.** Switching locale swaps the `[lang]` *root* layout, and Next's soft-navigation scroll handler picks the wrong node for that transition: clicking DE from the top of `/en` dropped the reader ~6100px down `/de`, into the footer. Oddly it inverted — starting scrolled went to the top, starting at the top went to the bottom. A real document navigation always starts at the top, and a locale switch is a new document anyway. The chat page keeps `<Link>`: it already behaved, and a reload there would throw away the conversation. Covered by the last three assertions in [i18n.test.js](frontend/tests/i18n.test.js).
- **The bare domain always lands on English, by design.** `/` 301s to `/en` at the edge so both locales stay static and edge-cached; there is no `Accept-Language` redirect. German visitors are caught instead by [frontend/src/app/lang-hint.js](frontend/src/app/lang-hint.js), a dismissible banner (choice remembered in `localStorage`) shown only when `navigator.language(s)` matches the *other* locale. It renders `null` on the server and on first paint — it is gated on a browser API, so committing to a visible state before mount would be a hydration mismatch. Mounted on the portfolio only: the chat page's fixed input bar sits where the banner would. It is anchored bottom-**left**, not centred — the portfolio keeps its primary buttons in the centre column and a centred banner covered the "Chat with Digital Twin" CTA; and it uses `left`+`right`+`margin-inline:auto` rather than `left:50%`+`translateX`, because a fixed element with only `left` set shrink-to-fits against the space from that offset to the viewport edge, which squeezed it to a 56px-wide, six-line column on a phone.
- **Frontend Next.js is non-standard.** [frontend/AGENTS.md](frontend/AGENTS.md) (referenced by [frontend/CLAUDE.md](frontend/CLAUDE.md)) warns it has breaking changes from training-data Next.js — read `node_modules/next/dist/docs/` before writing frontend code.
- **A "site is down / lost connection to the brain" report is usually the circuit breaker, not an outage.** Check `aws apigatewayv2 get-stage --api-id <id> --stage-name '$default' --query DefaultRouteSettings`: `0/0` means the breaker is engaged. It now auto-reopens when the alarm clears, but a *sustained* flood keeps it shut by design. A 429 carries no CORS headers, so the browser reports it as a **CORS error** — misleading, but the root cause is throttling.
- **Token streaming is not a small change here — three constraints stack.** Researched 2026-08-26 and deliberately not done. (1) Lambda supports response streaming on Node.js managed runtimes only; Python needs a custom runtime or the Lambda Web Adapter. (2) Function URLs *cannot* stream from inside a VPC, and the API Lambda must be in the VPC to reach RDS — so that route is closed, not merely awkward. (3) Response streaming through API Gateway exists for **REST** APIs only (since Nov 2025); this is an HTTP API (`aws_apigatewayv2_api`). Doing it therefore means migrating HTTP API → REST API, hand-writing CORS, adding the Web Adapter, and re-pointing [breaker.tf](terraform/breaker.tf) — which throttles via `apigatewayv2` calls that do not exist on a REST API, i.e. the abuse defence has to be rebuilt. Measured baseline without it: ~1190 ms for an English first question, ~1737 ms for German.
- **The chat page is an app shell pinned to `window.visualViewport`, not `100dvh`.** `dvh` does not shrink when the mobile keyboard opens, which leaves the input bar floating or hidden. [frontend/src/app/\[lang\]/avatar/avatar-client.js](frontend/src/app/[lang]/avatar/avatar-client.js) sets the root height from `visualViewport.height` and collapses the identity header while the keyboard is open. Auto-scroll must target the message container directly — `scrollIntoView()` walks scrollable ancestors and pans the whole shell on iOS. The input is a `<textarea>`, not an `<input>`: Enter sends, Shift+Enter inserts a newline, and it grows to `MAX_TEXTAREA_PX` before scrolling internally. Enter is ignored while `isComposing`, where it commits an IME candidate rather than meaning "send", and reader messages render `pre-wrap` or those newlines collapse. The reader's name lives in `localStorage` and is read in an effect, never during render — reading it during render would put a different value in the server HTML than in the first client paint.
- **Two things in [terraform.yml](.github/workflows/terraform.yml) exist because they failed in production, not as style.** `setup-python` must **not** re-gain `cache: 'pip'`: it is keyed on the same `requirements.txt` hash as the build-directory caches, so both hit together, `build.sh` then skips `pip install`, `~/.cache/pip` is never created, and setup-python's post step fails the whole job *after* terraform has already applied. And the `concurrency` group must keep `cancel-in-progress: false` — terraform holds a DynamoDB state lock for the length of a plan/apply, two pushes a minute apart is enough for the second to die on `ConditionalCheckFailedException`, and cancelling a run mid-apply would drop the lock with state half-written.
- **`data/` and the portfolio component can drift, and the twin then contradicts the page it sits on.** The certification list and years-of-experience live in *both* [data/](data/) (what the twin retrieves) and [portfolio-client.js](frontend/src/app/[lang]/portfolio-client.js) / the dictionaries (what the page shows), with no check tying them together. As of 2026-08-24 they disagree: the page lists AWS Certified AI Practitioner where `data/05_certifications.txt` lists SysOps Administrator, and the hero says "over 4 years" where `data/01_professional_summary.txt` says "6+ years". Changing one means changing the other.
- **The architecture diagram is generated, not drawn.** [scripts/generate_diagram.py](scripts/generate_diagram.py) renders `frontend/public/architecture.png`, which the README embeds. It drifted from reality once already; re-run `python scripts/generate_diagram.py` and commit the PNG whenever infrastructure changes meaningfully.
- **`frontend/public/twin-cover.png` is generated too, but its source is not in this repo.** It is served as `og:image` from [frontend/src/app/\[lang\]/layout.js](frontend/src/app/[lang]/layout.js), so a stale cover appears on every shared link. The HTML source and its renderer are kept outside version control (marketing assets, see `.gitignore`); ask the author to regenerate rather than hand-editing the PNG.
- **The breaker Lambda has no `build.sh`.** It is a single dependency-free file, so Terraform packages it with `archive_file` ([terraform/breaker.tf](terraform/breaker.tf)); `lambdas/breaker/breaker.zip` is a build artifact and is not committed. Only the API and ingestion Lambdas need their zips built before an apply.
- **Per-request timings are logged, and are the way to answer "why is it slow".** [lambdas/api/main.py](lambdas/api/main.py) logs `embed_ms`, `search_ms`, `generate_ms`, `rewrite_ms`, `chain_ms`, `docs_retrieved` and `lang` on every chat request (`rewrite_ms` is 0 when the query rewrite was skipped), queryable in Logs Insights. Measured split: generation ~84%, embedding ~13%, pgvector ~1.4%. `docs_retrieved` dropping to 0 is the empty-knowledge-base failure above, so it is the field to alarm on.

## Commands

**Local dev (both services):**
```bash
./scripts/start.sh   # backend uvicorn :8000 (creates/uses lambdas/api/venv), frontend next dev :3000
./scripts/stop.sh
```

**Backend only** (from `lambdas/api/`, venv activated): `uvicorn main:app --port 8000 --reload`
Local ingestion into the DB (needs `DATABASE_URL` in `lambdas/api/.env` — copy from `.env.example`): `python lambdas/api/ingest.py`

**Frontend** (from `frontend/`): `npm install`, `npm run dev`, `npm run build`

**Build Lambda deployment zips** (run before Terraform if Lambda code changed):
```bash
cd lambdas/api && ./build.sh          # -> lambdas/api/api_lambda.zip
cd lambdas/ingestion && ./build.sh    # -> lambdas/ingestion/lambda_function.zip
```

**Infrastructure** (from `terraform/`): `terraform init`, `terraform plan`, `terraform apply`.
Requires `terraform.tfvars` (copy from `terraform.tfvars.example` — sets `alert_email`; secret and gitignored). Amplify pulls the repo via the Amplify GitHub App; `github_token` is only needed as a one-time setup token if the Amplify app is ever recreated from scratch.

**Pre-commit hooks** (enforce `terraform fmt` + `terraform validate`): `pre-commit install`

**Frontend browser tests** (from `frontend/`, against a production build — `npm run build && npx next start -p 3100 &`):
```bash
npm run test:i18n        # 26 assertions: locales, metadata, language hint, toggle scroll
npm run test:chat        # 25 assertions: Enter/Shift+Enter, reader name, nav layout
npm run test:i18n:sweep  # diffs every visible string between /en and /de
```
They need `playwright` (a devDependency) plus a one-time `npx playwright install chromium`.

The **backend** has no formal test suite: [lambdas/api/test_lambda.py](lambdas/api/test_lambda.py) is an ad-hoc verification script, not a `pytest` harness.

## Deployment

Primary path is CI/CD: pushing to the deploy branch runs [.github/workflows/terraform.yml](.github/workflows/terraform.yml) (builds both Lambda zips, then `terraform fmt`/`validate`/`plan`/`apply`) via AWS OIDC — no static credentials. On PRs it posts the plan as a comment but does not apply. Local `terraform apply` works too but expects an `AWS_PROFILE`/credentials with the scoped permissions.
